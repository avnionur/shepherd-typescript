## Method

1. Enumerate assets and trust boundaries in the threat model and apply STRIDE per boundary.
2. For each threat, locate the mitigation in `src/` and a test in `test/` that exercises it; a
   threat without both becomes a finding.
3. Investigate the seed findings named in #187 by reading the code path and, where behavior depends
   on the host, by an empirical probe against `src/index.ts` on the reference host.
4. Assign severity with the rubric below, an owning slice, and a status. A critical finding must
   have an owning slice before the slice that records it can close.

Reference host for probes: macOS arm64, APFS, Node 24.17.0, process umask `022`.

## Severity rubric

| Severity | Definition |
| --- | --- |
| Critical | Without preconditions beyond using a documented API or CLI command as documented: a canonical record, cut, or receipt is silently forged, altered, or reinterpreted and still verifies; an effect or process escapes a placement reported as jailed; code runs from data (archive, record, task value, provider response) without a declared runner; or a supported default exposes secrets to another principal. |
| High | The same impact with a realistic precondition (caller misuse the docs do not warn against, local attacker with the caller's file access), or a persistent confidentiality loss that cannot be undone because records are immutable. |
| Medium | Local information disclosure to another OS user, denial of service from untrusted input a caller is documented to accept, or a missing verification layer whose absence is compensated elsewhere. |
| Low | Defense-in-depth gaps, hardening of trusted inputs, documentation overclaims, or process gaps without a direct exploit path. |

Statuses: `open` (owning slice will fix), `fixed` (fix and evidence landed), `accepted` (residual
risk documented in the threat model, re-examined by #29, or accepted by a recorded owner decision),
`owner-owed` (only the owner can close).
