# Generated API reference

The checked-in and packaged [API reference](./generated/api-reference.md) is the authoritative
symbol index for every supported package entry. It is generated from the emitted declaration
targets named by `package.json`, not from implementation modules or a separately maintained list.

## Generator and configuration

The repository-owned generator in `tooling/api-reference/generator.ts` uses the pinned TypeScript 7
compiler API. TypeDoc 0.28 does not declare TypeScript 7 compatibility, while API Extractor 7.59
carries a separate TypeScript 5.9 compiler; using the existing compiler keeps declaration
resolution aligned with the package build and adds no dependency lifecycle scripts or lockfile
authority.

`api-reference.config.json` owns the artifact and emitted-declaration roots, shared runtime
statement, source-origin/leakage policies, and each entry's title, domain summary, and
authority/mutation note. The configured entry keys must exactly match the package export map, so
adding or removing a supported subpath fails generation until its documentation ownership is
explicit. Package name, version, Node engine, declaration targets, and exported symbols remain
derived from `package.json` and emitted declarations.

Generate or check the reference with:

```sh
pnpm generate:api-reference
pnpm check:api-reference
```

Generation first builds declarations. Ordinary `pnpm verify` builds and then runs check mode, which
compares generated bytes with the checked-in artifact and rejects stale output.

## Reference contract

Each entry records:

- its supported import specifier and a typechecked namespace-import example;
- its Node/ESM requirement and domain-owned authority or mutation boundary;
- every symbol resolved by the TypeScript checker from that entry;
- whether the symbol is `type-only`, `runtime-only`, or `runtime-and-type`;
- emitted signatures, including generics and public class/interface members;
- declaration JSDoc summaries, parameters, return values, thrown-error contracts, examples, and
  other public tags;
- `Status: deprecated` on the classification line and a `Deprecated:` section for exports tagged
  `@deprecated`, whose text must name the deprecating release (for example
  `@deprecated Since 2.27.0. Use ... instead.`).

`readPublishedApi` in the same module exposes the symbols, kinds, printed declarations, and tags
that the reference renders. The [compatibility gate](./compatibility-policy.md) fingerprints that
surface, so the documented API and the enforced API are the same set.

The root and domain entries intentionally repeat shared exports. This makes each supported import
surface complete in isolation and allows export drift to be reviewed at the same boundary a
consumer imports.

## Security and privacy boundary

The generator opens only emitted `.d.ts` targets from the package export map. Resolved declarations
must remain inside the configured emitted declaration tree. Configuration rejects source origins
owned by private codecs, migrations, SQL/store implementation, protocol configuration,
non-public validators, or credentials. A supported top-level export marked `@internal` fails
generation; private, protected, `#private`, and `@internal` class/interface members are excluded.

Configured leakage checks reject internal annotations, private declaration members, dependency or
host-local paths, and credential-bearing declarations. The resulting reference therefore exposes
no private deep-module inventory, migrations, codecs, SQL implementation, protocol configuration
objects, credentials, local paths, or stacks. Public validation helpers and public store classes
remain documented only when they resolve from a supported entry.

Fresh-package conformance verifies that the generated artifact is present and byte-identical after
install, then typechecks a consumer namespace import for every declared export subpath. Existing
CommonJS `require()` loading, deep-import refusal, map-free and internal-free declarations, root quickstart, CLI redaction, recovery,
settlement, and native-platform behavior remain owned by their existing verification seams.
